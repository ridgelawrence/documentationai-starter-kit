## Portal setup

Start by confirming the basics of your workspace. A clear portal setup helps your users find the right services quickly and reduces support friction later.

<Steps>
  <Step title="Sign in to the portal" icon="login">
    Open the WRLD portal and verify that you are using the correct account for your division. If you manage more than one workspace, confirm that the active workspace matches the one you want to configure.
  </Step>
  <Step title="Review your workspace profile" icon="settings">
    Update the workspace name, contact email, and default language. Keep these values consistent with your internal records so ticket routing stays accurate.
  </Step>
  <Step title="Save your preferences" icon="check-circle">
    Save the changes and refresh the portal to confirm the updated settings appear in your dashboard and support views.
  </Step>
</Steps>

## Access permissions

Use permissions to control what each person can see and do. Most teams only need a few roles at first, then add more granular access as the workspace grows.

| Role | Can view tickets | Can manage billing | Can edit workspace settings |
|------|-------------------|--------------------|-----------------------------|
| Admin | Yes | Yes | Yes |
| Support Agent | Yes | No | No |
| Billing Contact | Limited | Yes | No |
| Viewer | Read-only | No | No |

<Callout kind="tip">
  Keep admin access limited to the smallest practical group. That makes audits easier and reduces accidental changes.
</Callout>

## Support channels

Choose the support path that fits your team’s workflow. Some divisions prefer direct email, while others rely on the ticket portal for traceability and handoff.

<Tabs>
  <Tab title="Email" icon="mail">
    Use a shared inbox when your team wants simple routing and fast replies.

    ```text
    helpdesk@wrld.tech
    ```

    Create a rule set that forwards division-specific requests to the right queue.
  </Tab>
  <Tab title="Portal tickets" icon="file-text">
    Use ticket submission when you need a full audit trail, status tracking, and internal assignment.

    ```text
    https://help.wrld.tech/support/submit-ticket
    ```

    Ask users to include the workspace name, issue summary, and impact level.
  </Tab>
  <Tab title="Dashboard" icon="monitor">
    Use the dashboard for account-level actions such as service review, access checks, and subscription management.

    ```text
    https://dashboard.example.com
    ```

    Make sure each user sees only the data tied to their role.
  </Tab>
</Tabs>

## Workspace preferences

The following settings are useful when you want a consistent experience across divisions. They help you standardize notifications, working hours, and local preferences without overcomplicating the setup.

<CodeGroup tabs="JSON,YAML,Bash">
  ```json
  {
    "workspaceName": "WRLD Tech Co.",
    "defaultChannel": "portal",
    "supportEmail": "helpdesk@wrld.tech",
    "notifications": {
      "ticketUpdates": true,
      "weeklySummary": true,
      "securityAlerts": true
    }
  }
  ```
  ```yaml
  workspaceName: WRLD Tech Co.
  defaultChannel: portal
  supportEmail: helpdesk@wrld.tech
  notifications:
    ticketUpdates: true
    weeklySummary: true
    securityAlerts: true
  ```
  ```bash
  export WRLD_WORKSPACE="WRLD Tech Co."
  export WRLD_SUPPORT_CHANNEL="portal"
  export WRLD_SUPPORT_EMAIL="helpdesk@wrld.tech"
  ```
</CodeGroup>

## Advanced options

<Expandable title="How do you handle multiple divisions?" default-open="false">
  
Use separate workspaces when each division needs different permissions, service queues, or notification rules. If your divisions share the same operational team, you can keep one workspace and route requests by category instead.

</Expandable>

<Expandable title="What should you document first?" default-open="false">
  
Start with access rules, support contacts, and the default workflow for handling requests. Those three items remove the most confusion for new users.

</Expandable>
