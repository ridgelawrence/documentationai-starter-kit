## Overview

WRLD Tech is a documentation hub for a multi-division organization. You use it to understand how the divisions relate to one another, where to find the right entry point, and how the public directory and private portal fit together.

The core idea is simple: one hub, many divisions. You browse shared guidance from the central help center, then move into the division that matches your task, product, or support need.

<Callout kind="info">

This page is a starter kit template. Adapt the division names, links, and terminology to match your real organization structure.

</Callout>

## How the WRLD structure works

At a high level, you can think about WRLD as a set of connected surfaces:

- The help center provides public documentation and guidance.
- The directory helps people discover the wider WRLD ecosystem.
- The portal gives logged-in users a place to manage their account or services.
- Each division owns its own content, workflows, and terminology.

This structure keeps content organized without forcing every audience into the same path. You can publish broad concepts in the hub, then link to specific division pages for deeper workflows.

## Shared terminology

When you write or read WRLD documentation, keep the terminology consistent. That makes it easier to scan the hub and understand what belongs where.

| Term | Meaning | Example use |
|------|---------|-------------|
| Division | A major WRLD business area with its own scope | WRLD.host, WRLD.design |
| Hub | The shared documentation center | WRLD Tech docs |
| Directory | A public index of WRLD properties | The wider WRLD directory |
| Portal | A signed-in user workspace | Client portal |
| Support path | The route to help or escalation | Open a ticket or email support |

Use the same naming pattern everywhere you can. If your audience sees a term in one place and a different label elsewhere, they may assume those are two separate systems.

## Example content model

If you are building or revising pages, keep the content model simple and repeatable. A good pattern is to define the audience, explain the concept, show the path, and then link to the next action.

```javascript
const wrldNavigation = {
  hub: "WRLD Tech Docs",
  divisions: ["WRLD.tech", "WRLD.host", "WRLD.design", "WRLD.Services", "WRLD.Support", "WRLD.AI"],
  publicEntry: "/",
  portalEntry: "https://portal.wrld.tech",
  directoryEntry: "https://wrld.one"
};

export default wrldNavigation;
```

The example above shows how a shared navigation object can keep labels consistent across your site. You can adapt the same pattern for menus, breadcrumbs, or help-center sidebars.

## Best practices

- Keep division names stable and easy to scan.
- Use one primary term for each concept.
- Link from the hub to the most relevant division page.
- Reserve the portal for authenticated workflows.
- Keep public and private content clearly separated.

<Expandable title="When should you add a new division page?" default-open="false">

Add a new page when a division has distinct users, workflows, or support paths. If the content is just a variation of an existing topic, extend the current page instead of creating a duplicate.

</Expandable>

<Expandable title="How do you keep documentation consistent?" default-open="false">

Use shared terminology, reuse the same navigation labels, and keep examples aligned with the current structure. A small style guide prevents confusion later.

</Expandable>
